# AB#1647843

## Executive Summary

When someone opened an everyday dialog or drawer on a desktop-sized screen, the page behind it kept scrolling. The blocking version of the same component held the page still correctly. The result was that two presentations of the same component behaved differently for no reason a user or a developer could predict, and content drifted out of view while someone was reading the panel in front of it.

The behavior that freezes the page lives in shared code used by every Auro overlay, so neither of the two components that reported the problem could correct it on their own. This change fixes it in that shared code: any panel laid over the page now holds the page still, panels that open inside a region of the page keep scrolling as before, and the page is always handed back when the panel closes or is removed.

Ticket: [AB#1647843](https://itsals.visualstudio.com/E_Retain_Content/_workitems/edit/1647843) — *Freeze the page behind any overlay that covers it, not only full-screen ones*

This single fix resolves two separately reported bugs: AB#1625424 (`auro-dialog`) and AB#1625435 (`auro-drawer`). There is no visual change and no change to how any component is used.

## The Problem

Two bugs were filed independently, in two different components, describing the same thing:

- **AB#1625424** — with a default, dismissible dialog open, the page behind it still scrolls with the mouse wheel, trackpad, touch, or the arrow and space keys.
- **AB#1625435** — the same symptom, in the drawer.

In both cases the blocking presentation of the component worked correctly. Only the everyday, dismissible one was affected, and only when the browser window was wider than the point at which the panel stops filling the screen. On a phone, both worked.

Letting the background scroll behind an open panel is disorienting. Content drifts out of view while the reader is held inside the panel, and on touch devices and with a screen reader the page can move unexpectedly. It also made two presentations of the same component behave inconsistently.

A second, related gap was reported in the same ticket: if a panel was removed from the page while still open, the page was never given back and could be left permanently unable to scroll.

## Root Cause

All of this sits in `scripts/runtime/floatingUI.mjs`.

`lockScroll()` was already a thorough implementation — `scrollbarGutter: stable` and `overflow: hidden` on `<html>`, `overflow: hidden` plus `position: fixed; top: -<scrollY>px; width: 100%` on `<body>` (the only reliable way to block the VoiceOver three-finger swipe), a `touchmove` blocker that still permits scrollable descendants, continuous `visualViewport` tracking for the iOS virtual keyboard, and full restoration of the previous inline styles and scroll offset.

The defect was in what gated it. `getPositioningStrategy()` resolves dialog and drawer behavior as:

```js
return smallerThanBreakpoint || this.element.modal ? "fullscreen" : "dialog";
```

and `configureBibStrategy()` was the sole gate on the lock:

```js
if (element.isPopoverVisible) {
  this.lockScroll(value === "fullscreen");   // ← the bug
}
```

A dismissible dialog or drawer above the breakpoint resolves to `"dialog"` and therefore reached `lockScroll(false)`. Positioning strategy and scroll ownership are different concerns: `"fullscreen"` and `"dialog"` are both overlays laid over the page with focus trapped inside them, differing only in size. Every other side effect in the same branch already treated them identically — only the `lockScroll` argument singled out `"fullscreen"`.

Two factors made it worse:

- **The gate re-runs.** `position()` calls `configureBibStrategy()`, and `showBib()` registers Floating UI's `autoUpdate`, so this line executes on every resize and scroll tick while the overlay is open. The lock was not merely skipped — it was actively *released*, repeatedly. Any component-side workaround would have been torn down within a frame, which is why neither consumer could fix it locally.
- **Crossing the breakpoint masked it.** Below the breakpoint the strategy flips to `"fullscreen"` and the lock engages, so the bug was invisible on narrow viewports and on mobile — the configurations most likely to be spot-checked for scroll behavior.

**Secondary defect.** `lockScroll(false)` was reachable from exactly one place, `hideBib()`. `disconnect()` never called it, so unmounting a component while its overlay was open stranded `body { position: fixed }` with no code path left to undo it. Both consumers had previously owned this cleanup themselves (`auro-dialog` `e12bd72`, `auro-drawer` `be314cb`) and both lost it when the lock moved into the library.

The common thread across every defect found here: the lock is a single global resource, but the decision to take or release it was spread across `configureBibStrategy()`, `hideBib()`, `disconnect()`, and `configure()`, each deciding locally.

## The Fix

Twelve changes, all in `scripts/runtime/floatingUI.mjs`.

1. **Lock for the whole overlay branch.** The enclosing guard is already `value === "fullscreen" || value === "dialog"`, so the call becomes unconditional within it: `this.lockScroll(true)`. The nested `"cover"` strategy takes the `else` branch and is untouched.

2. **Release on teardown.** `disconnect()` now calls `this.lockScroll(false)`.

3. **Make the unlock path independent of the bib.** `lockScroll()`'s `if (!element?.bib) return;` guard now applies only to the lock direction, so a floater whose bib has already been detached can still be unlocked — the exact situation `disconnect()` runs in.

4. **Give the non-overlay branch the mirror responsibility.** The `else` branch now opens with `this.lockScroll(false)`. Declining to take a lock is not the same as handing one back: a dropdown opened on a narrow viewport locks, and widening the window lands it in the `else` branch while still open, freezing the page behind a small floating bib.

5. **Separate teardown from rewiring.** `disconnect({ teardown = true } = {})` takes an explicit intent, and `configure()` passes `{ teardown: false }`. `configure()` runs on every `triggerElement` change, so an unconditional unlock there released the page behind an overlay that was still open. The default keeps every external caller unchanged.

6. **Scope the `aria-modal` removal to the instance that set it.** The mirroring sat *above* `lockScroll()`'s `_scrollLocked` guards, so only the write was owner-gated; the removal ran on every `lockScroll(false)`, and fix 4 made every non-owning instance call that on every `autoUpdate` tick. A repositioning dropdown therefore stripped `aria-modal` off an open modal dialog it had nothing to do with. Extracted to `mirrorAriaModal()`.

7. **Rewiring must put back what teardown removed.** `{ teardown: false }` keeps the lock, but `cleanupHideHandlers()` and `element.cleanup?.()` still run, and the trigger listeners `configure()` re-registers replace neither. An overlay open across a `triggerElement` change was left on screen, frozen, dismissable only via its original trigger. `showBib()`'s dismissal setup is factored into `setupDismissHandlers()` and re-run with `autoUpdate` when showing.

8. **Cancel the pending `configureBibStrategy()` retry on teardown.** The method self-schedules a `setTimeout(…, 0)` retry when it cannot find a `.container` in the bib's shadow root. The id was never stored, so a retry firing a macrotask after `disconnect()` re-entered with `isPopoverVisible` still true and took the lock straight back, with the floater already gone. Not the rare race it reads as: `auro-dialog`'s `#bib` is a plain `<div>` whose `.container` is a sibling in the host's shadow root, so the condition can never become true and it retries the full `MAX_CONFIGURATION_COUNT` on every floater.

9. **Consumer half — `auro-dialog` must not tear down on a DOM move.** `disconnectedCallback` also fires on a same-document reparent. Teardown is now deferred one microtask and skipped if the element reconnected. Paired with a `connectedCallback` rewire so a genuine cross-task remount comes back live rather than dead. *(Shipped in `auro-dialog`; recorded here because it is half of this fix.)*

Three further fixes came from PR review on #301 (reviewer: sun-mota), all in the element-swap path added by fix 5:

10. **Tear down against the outgoing element.** `configure()` assigned `this.element = elem` *before* calling `disconnect()`, so on a genuine element swap every element-scoped release aimed at the incoming element: the outgoing dialog kept `aria-modal="true"` permanently, its bib transform was never restored, and the incoming bib had the outgoing element's saved transform written onto it. The `element.trigger` gate also read the incoming element's trigger — not assigned until later in the method — so teardown was usually skipped outright, leaving the page locked with no owner. The teardown now runs before the repoint.

11. **Clear `showing` on a swap.** `disconnect()` never resets `this.showing`, and the rewire block that would is gated on a same-element rewire. Left `true`, the incoming element's first `showBib()` was silently dropped by its own `!this.showing` guard and the overlay never opened.

12. **Re-assert `aria-modal` while the lock is held.** Fix 6 placed the mirror inside `lockScroll()`'s `!_scrollLocked` guard, so it fired only on the unlocked → locked transition. A bib re-render that replaced the inner `<dialog>` mid-lock left the replacement unmarked until a full unlock/lock cycle. The write now runs on every lock call and skips when the attribute already reads correctly; the *removal* stays inside the guard, preserving fix 6.

## Why This Works

**The invariant now stated once.** Scroll ownership is a property of being an overlay, not of how the overlay is sized. `"fullscreen"` and `"dialog"` both lay the bib over the page and trap focus inside it; `"cover"` and `"floating"` do not. Both branches of `configureBibStrategy()` now state their side of that rule, so the lock is taken and handed back by the same decision rather than inferred from an unrelated enum.

**Scope is provably narrow.** `new AuroFloatingUI(this, <behavior>)` with a behavior argument occurs only in `auro-dialog` and `auro-drawer`. Every other consumer constructs with no behavior and resolves to `"floating"`/`"fullscreen"`. `getPositioningStrategy()`'s `default` case passes unknown behaviors through verbatim, so they never reach the overlay branch.

**Repeat locks cannot clobber consumer styles.** `lockScroll` is guarded by `_scrollLocked`, and `_savedScrollStyles` identity is asserted across three consecutive reconfigurations. Pre-existing values are captured and restored, not wiped.

**`aria-modal` on dismissible overlays was reviewed and kept.** `lockScroll()` sets `aria-modal="true"` as part of locking, so dismissible dialogs and drawers now carry it. Both consumers already apply a `FocusTrap` to their non-modal presentations — `auro-drawer/src/auro-drawer-content.js:125-126` and `auro-dialog/src/componentBase.js:340`, neither gated on `modal` — so the attribute describes what actually happens, and it matches `auro-dropdown`'s existing mobile fullscreen path. Removing it while keeping the trap would be strictly worse: a screen reader user in browse mode could hear background content but not operate it. `auro-dialog`'s accessibility page claimed the page behind a non-modal dialog "remains reachable", already contradicted by its own focus-management section; that was corrected under AB#1625424.

**Coverage targets the requirement, not the implementation.** No test anywhere had asserted which strategies own the lock — the two existing `configureBibStrategy` tests both set `isPopoverVisible = false`, which is the guard on the `lockScroll` call, so **no test reached that line at all**. Downstream, `auro-dialog`'s only scroll assertion used a `modal` dialog and `auro-drawer` had no non-modal case. The suite now stands at 22 tests in a hermetic `scroll lock ownership` suite, with `does not make the lock conditional on modal` naming the guarantee directly rather than the code path that currently implements it.

**Every fix was verified by reverting it in isolation:**

| Reverted | Result |
|---|---|
| `lockScroll(value === "fullscreen")` restored | 6 tests fail |
| `disconnect()` unlock removed | exactly 1 fails |
| `else`-branch unlock removed | `releases the lock when an open overlay widens out of fullscreen` fails |
| `configure()`'s `{ teardown: false }` removed | `keeps the lock when configure() rewires the trigger while open` fails |
| `auro-dialog` deferred teardown reverted | the reparent test fails in both viewports |
| `lockScroll(Boolean(element.modal))` | **13 fail**, including `does not make the lock conditional on modal` |
| `aria-modal` mirroring moved back above the guards | `does not strip aria-modal set by a different overlay` fails |
| `configure()`'s dismissal-handler restoration removed | 2 fail |
| `disconnect()`'s `clearTimeout` removed | `does not re-lock the page when a pending retry fires after teardown` fails |
| `this.element = elem` moved back before `disconnect()` | `tears down against the outgoing element when configure() swaps elements` fails |
| `this.showing = false` removed | `clears showing when configure() swaps elements` fails |
| `mirrorAriaModal(true)` back inside the guard | `re-applies aria-modal to a dialog replaced while the lock is held` fails |

Two candidate fixes for the reconfigure defect were caught by the suite and rejected: guarding the unlock on `!isPopoverVisible` and on `!isConnected` both fail `releases the lock when the floater is torn down while open`, since both conditions still hold during a genuine teardown.

Full suites green: **164** in `auro-library`, **96** in `auro-dialog`, **116** in `auro-drawer`.

## Outcome

Everyday dialogs and drawers now hold the page still while they are open, exactly as the blocking versions already did, and return the reader to where they left off when the panel closes. Panels that open inside a region of the page still scroll as before. Removing a panel while it is open now always gives the page back, closing a gap that could previously leave a page unable to scroll at all until it was reloaded.

Two separately reported bugs are resolved by this one change. There is no visual change, no change to how any component is used, and no change for the components that were already behaving correctly.

## Ticket Completeness

Four of five requirements fully resolved; one resolved for every single-overlay case with a known gap when two overlays are open at once.

**Resolved**

- **The page behind an open dialog or drawer stays fixed.** The shared code now holds the page for any panel laid over it, not only full-screen ones.
- **The page returns to exactly where the reader left it when the panel closes.** The scroll position is captured when the panel opens and restored on close; covered by a test that scrolls the page first, since at offset zero the assertion proves nothing.
- **The everyday and blocking versions behave the same way.** Both presentations hold the page identically. A test names this requirement directly, so a future change that ties the behavior back to the blocking flag fails loudly.
- **Panels that open inside a region of the page keep scrolling as they do today.** Nested panels take a different path and are untouched, asserted by two tests.

**Not Resolved / Partial**

- **"Closing or removing a panel always gives the page back"** — resolved for every path involving a single panel: closing it, removing it while open, widening the window past the breakpoint while open, reconfiguring it while open, and a stale internal retry firing after removal are all now covered. The gap is two panels open at once. The saved page styles are stored per panel while the page itself is shared, so a second panel opening on top of a locked page saves the already-locked styles; closing them out of order can leave the page frozen with no owner. This predates the change, but the change widens exposure by making everyday desktop panels hold the page too. It is tracked as **AB#1648833**, which takes this change as its baseline. No test in any repo yet opens two panels at once, which is why it stays invisible.

## Learnings

- **A gate that re-runs is not a one-time decision.** `configureBibStrategy()` is invoked by `autoUpdate` on every resize and scroll tick, which turned a wrong condition into an active, repeated *un*-locking — and is why neither consuming component could patch around it. Before centralizing a behavior, check how often the deciding code path executes.
- **Do not gate one concern on another concern's enum.** Scroll ownership was inferred from positioning strategy because the two coincided for the cases that existed at the time. When the strategy set grew a non-fullscreen overlay, the inference silently broke. That every other line in the same branch already treated the two strategies identically was the tell.
- **A shared resource needs one owner, not a rule applied at each call site.** Every defect here is the same shape. Fixing one exposed the next — the lock and unlock branches disagreed, then teardown and rewiring disagreed, then the swap path disagreed with itself, and the per-instance snapshot still disagrees when two overlays are open. When a fix keeps uncovering siblings, the bug is the ownership model, not any one branch.
- **One method serving two intents will eventually serve the wrong one.** `disconnect()` meant both "tear this down" and "rewire this," which was harmless until it acquired a side effect only one of them wanted.
- **Order matters when state is element-scoped.** Fixes 10 and 11 both came from repointing `this.element` before running the teardown that releases that element's state. If a method both releases resources and retargets itself, release first.
- **Centralizing a behavior must move its tests too.** Both components deleted working scroll-lock code in favor of the library and deleted their coverage with it, while the library gained none. The behavior then had no owner asserting it in any repo.
- **Coverage that only exercises the working configuration is worse than none** — it produces a green suite that reads as proof. Both components had scroll-lock tests; both used the presentation that still worked. Confirm a new regression test fails with the fix reverted.
- **Name the guarantee in a test, not just the code path.** The original suite pinned "strategy `dialog` locks," which a later `modal`-gating proposal satisfied in the modal case while re-breaking the reported bug. `does not make the lock conditional on modal` states the requirement itself.
- **The requirement is evidence; a plausible mechanism argument is not.** A review pass reasoned from `showPopover()`'s semantics that background content stays keyboard reachable, concluded the lock was an a11y defect, and proposed gating it on `modal`. It was wrong twice: the components layer a `FocusTrap` over the popover, *and* the behavior it removed was the literal text of AB#1625424's Expected Results. Reading one half of a mechanism without the other inverted the conclusion.
- **A test-hygiene helper can hide the mess it was written to prevent.** The consumer suites' snapshot/restore helper faithfully put leaked page state back, so a leaking test was invisible to every test after it. Restoring prior state is right for values a test itself set; for global state a *previous* test may have corrupted, clearing is what makes a suite hermetic.
- **A fixture built to dodge a bug guarantees no test can find it.** The library suite gives the bib a shadow root with a `.container` specifically so the retry timer stops — which is exactly why fix 8's defect was invisible here and had to be found from the consumer side.

## Iterations That Didn't Work

- **Gating the lock on `element.modal`.** Proposed in review on the reasoning that non-modal overlays should leave background content reachable. Implemented and committed before the suite's breadth made clear what it had undone: it re-creates AB#1625424 exactly, and fails 13 tests including the one that names the requirement. Reverted. Its premise is contradicted by the `FocusTrap` both consumers apply on every path.
- **Guarding the teardown unlock on `!isPopoverVisible`, and separately on `!isConnected`.** Both were attempts to stop `configure()`'s rewire from releasing the lock. Both fail `releases the lock when the floater is torn down while open`, because both conditions still hold during a genuine teardown. Replaced by the explicit `disconnect({ teardown })` intent.
- **Splitting `disconnect()` into two methods** instead of adding the options argument. Rejected: `configure()` legitimately wants four of `disconnect()`'s five cleanup steps, so the two intents differ by exactly one statement. A split would have been the same semantics with more code motion and more room to mis-assign a step.
- **Copying `auro-drawer`'s teardown ordering into `auro-dialog`.** The drawer calls `hide("disconnect")` before `floater.disconnect()`, and `hideBib()` unlocks, so it never had fix 2's defect. Copying that was rejected because `closeDialog()` schedules the 300ms `hidePopover` timer that `disconnectedCallback` then clears — the dialog would have been left marked closed with its popover still on screen. The drawer's ordering has its own cost (a reparented drawer closes and fires a toggle event), tracked separately.
- **Asserting the reposition behavior by calling `configureBibStrategy()` directly.** The first draft of the consumer-side test did this and asserted the library's private `_scrollLocked`. It picked the strategy *for* the library, skipping `getPositioningStrategy()` — the resolution that decides whether an `auro-dialog` is an overlay at all, which is the actual gap behind the ticket. Replaced with a real viewport resize that waits on `autoUpdate`, asserting observable page state.
- **Asserting scroll restoration at offset zero.** The lock writes `top: -0px`, which the browser normalizes to `0px`, so the assertion passed while proving nothing. The test now scrolls the page first.
- **Trailing-statement cleanup in the consumer scroll-lock tests.** A failed `expect()` is exactly what those tests exist to produce, and it skips a trailing restore — leaving the page frozen so that one real regression cascaded into unrelated failures across both viewport passes. Replaced with an `onCleanup`/`afterEach` registry in `auro-dialog` and `try/finally` in `auro-drawer`.
