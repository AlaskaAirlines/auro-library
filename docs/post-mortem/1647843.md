# AB#1647843 — Page Scroll Lock Gated on Positioning Strategy Instead of Overlay-ness

**Scope:** 2 files changed in `auro-library` — `scripts/runtime/floatingUI.mjs` (`configureBibStrategy()`, `lockScroll()`, `disconnect()`, `configure()`) and `scripts/runtime/floatingUI.test.js` (14 new tests, plus an unlock added to one leaking pre-existing test). Companion dependency bumps, regression tests, and a `disconnectedCallback` change in `auro-dialog` (AB#1625424); dependency bump and regression tests in `auro-drawer` (AB#1625435). No public API surface change; `disconnect()` gains an optional options argument whose default preserves existing behavior.

## Executive Summary

A dismissible `auro-dialog` or `auro-drawer` left the page behind it scrollable at desktop widths, while the blocking (`modal`) presentation locked it correctly. `floatingUI` already contained a complete, hardened page scroll lock, but it was engaged only when the *positioning* strategy resolved to `"fullscreen"` — and a non-modal dialog or drawer above the fullscreen breakpoint resolves to `"dialog"`. Worse, because the gate lives in `configureBibStrategy()`, which Floating UI's `autoUpdate` re-runs on every resize and scroll tick, the code did not merely fail to lock: it actively *released* the lock repeatedly while the overlay was open. The fix decouples scroll ownership from positioning strategy — both overlay strategies lock, the nested `"cover"` strategy does not. Three further defects in the same ownership model were found and fixed alongside it: nothing released the lock when a floater was torn down while still open; the teardown unlock then fired on a *reconfigure* and on a DOM *reparent*, releasing the lock out from under an overlay that was still visible; and the non-overlay branch never handed the lock back, so an overlay that locked while narrow stayed locked after widening past the breakpoint. The common thread is that the lock's ownership was expressed implicitly, as a side effect of several unrelated code paths, rather than as a single stated rule.

---

### Section 1 — The Problem

Two independently filed bugs described identical symptoms in two components:

- **AB#1625424** (`auro-dialog`) — with a default, dismissible dialog open, the page behind it still scrolls via wheel, trackpad, touch, and arrow/space keys. The `modal` dialog does not.
- **AB#1625435** (`auro-drawer`) — same wording, same symptom.

Letting the background scroll behind an open overlay is disorienting: content drifts out of view while the reader is held inside the overlay, and on touch devices and with screen readers the page can move unexpectedly. It also made the everyday and blocking presentations of the same component behave differently for no reason a consumer could predict.

Both components had delegated this behavior to `floatingUI` and neither could correct it locally, which is what made this a library bug rather than two component bugs.

---

### Section 2 — Root Cause (Code-Level)

Three pieces of `scripts/runtime/floatingUI.mjs` combined:

1. `lockScroll(lock)` — a thorough implementation: `scrollbarGutter: stable` and `overflow: hidden` on `<html>`, `overflow: hidden` plus `position: fixed; top: -<scrollY>px; width: 100%` on `<body>` (the only reliable way to block the VoiceOver three-finger swipe), a `touchmove` blocker that still permits scrollable descendants, continuous `visualViewport` pan tracking for the iOS virtual keyboard, and full restoration of the previous inline styles and scroll offset.

2. `getPositioningStrategy()` — for `dialog` and `drawer` behavior (they share one branch):

   ```js
   return smallerThanBreakpoint || this.element.modal
     ? "fullscreen"
     : "dialog";
   ```

3. `configureBibStrategy(value)` — the sole gate on the lock, inside the branch taken for both `"fullscreen"` and `"dialog"`:

   ```js
   if (element.isPopoverVisible) {
     this.lockScroll(value === "fullscreen");   // ← the bug
   }
   ```

So a dismissible dialog or drawer above the fullscreen breakpoint resolved to `"dialog"` and reached `lockScroll(false)`. Positioning strategy and scroll ownership are different concerns: `"fullscreen"` and `"dialog"` are both overlays laid over the page with focus trapped inside them and differ only in how large they are. Every other side effect in `configureBibStrategy` already treats the two identically — only the `lockScroll` argument singled out `"fullscreen"`.

Two aggravating factors:

- **The unlock was not a one-time miss.** `position()` calls `configureBibStrategy()`, and `showBib()` registers Floating UI's `autoUpdate`, so this line re-runs on every resize and scroll tick while the overlay is open. Any component-side lock would have been torn down again within a frame, which is why neither consumer could work around it.
- **Crossing the breakpoint masked it.** Below the breakpoint the strategy flips to `"fullscreen"` and the lock engages, so the bug was invisible on narrow viewports and on mobile — the configurations most likely to be spot-checked for scroll behavior.

**Secondary defect.** `lockScroll(false)` was reachable from exactly one place, `hideBib()`. `disconnect()` never called it, so unmounting a component while its overlay was open stranded `body { position: fixed }` on the page with no code path left to undo it — a permanently unscrollable page. Both consumers had previously owned this cleanup themselves (`auro-dialog` `e12bd72`, `auro-drawer` `be314cb`) and both lost it when the lock moved into the library.

---

### Section 3 — The Fix

**1. Lock for the whole overlay branch.** The enclosing branch guard is already `value === "fullscreen" || value === "dialog"`, so the call becomes unconditional within it:

```js
if (element.isPopoverVisible) {
  this.lockScroll(true);
}
```

The nested `"cover"` strategy takes the `else` branch and is untouched — a nested overlay is positioned inside its parent rather than over the page, so it stays scrollable by design.

**2. Release on teardown.** `disconnect()` now calls `this.lockScroll(false)` before its `!element` early-return.

**3. Make the unlock path independent of the bib.** `lockScroll()` opened with `if (!element?.bib) return;`, which meant a floater whose bib had already been detached could not be unlocked — the exact situation `disconnect()` runs in. The guard now applies only to the lock direction:

```js
if (lock && !element?.bib) {
  return;
}
```

The `aria-modal` mirroring below it was made null-safe for the same reason. The rest of the unlock path was already written with optional chaining.

**4. Give the non-overlay branch the mirror responsibility.** Fixes 1–3 stated where the lock is *taken* but left the `else` branch silent, and declining to take a lock is not the same as handing one back. `getPositioningStrategy()` returns `"fullscreen"` below the breakpoint and `"floating"` above it for `dropdown` behavior, and `autoUpdate` re-runs this method on every resize tick — so a dropdown opened on a narrow viewport locks, and widening the window lands it in the `else` branch while still open. The page then stayed frozen behind a small floating bib until `hideBib()` happened to run. The branch now opens with `this.lockScroll(false)`. This defect predates the ticket; it is fixed here because this is the change that makes lock ownership an explicit rule, and a rule stated for only one branch is not a rule.

**5. Separate teardown from rewiring.** Fix 2 made `disconnect()` unlock unconditionally, which was too broad: `disconnect()` is not only a teardown path. `configure()` calls it on every `triggerElement` change (both consumers do this from `updated()`), so re-configuring an open overlay released the page behind it *and* ran `window.scrollTo(0, _savedScrollY)` on a page that was still `position: fixed`. `disconnect()` now takes an explicit intent:

```js
disconnect({ teardown = true } = {}) {
  // …
  if (teardown) {
    this.lockScroll(false);
  }
```

and `configure()` passes `{ teardown: false }`. The default keeps every external caller byte-for-byte unchanged. This shape was chosen over splitting the method because `configure()` legitimately wants four of `disconnect()`'s five cleanup steps — the two intents differ by exactly one statement, so a split would have been the same semantics with more code motion and more room to mis-assign a step.

**6. Consumer half: `auro-dialog` must not tear down on a DOM move.** `disconnectedCallback` also fires on a same-document reparent, where teardown intent is genuine but the element comes straight back. `auro-dialog` called `floater.disconnect()` directly, so a reparented open dialog returned visible over a page that scrolled freely, with `autoUpdate` gone and nothing left to re-lock it — the AB#1625424 symptom by another route. Its teardown is now deferred one microtask and skipped if the element reconnected:

```js
queueMicrotask(() => {
  if (this.isConnected) {
    return;
  }
  this._teardown();
});
```

`auro-drawer` never had this defect: it calls `hide("disconnect")` before `floater.disconnect()`, and `hideBib()` unlocks. That ordering has its own cost — a reparented drawer *closes*, reflecting `open` off and firing a toggle event — which is tracked separately as a behavior improvement rather than fixed here. Copying drawer's ordering into dialog was considered and rejected: `closeDialog()` schedules the 300ms `hidePopover` timer that `disconnectedCallback` then clears, so the dialog would have been left marked closed with its popover still on screen.

**Deliberately not changed: `aria-modal`.** `lockScroll()` sets `aria-modal="true"` on the inner `<dialog>` as part of locking, so dismissible dialogs and drawers now carry it. This was reviewed and kept: both consumers already apply a `FocusTrap` to their non-modal presentations, so `aria-modal="true"` describes what actually happens, and it matches what `auro-dropdown` already does on its mobile fullscreen path. `auro-dialog`'s accessibility documentation claimed the page behind a non-modal dialog "remains reachable" — already contradicted by its own focus-management section — and is corrected as part of AB#1625424.

### Section 4 — Test Coverage

No test anywhere asserted which strategies own the lock. The two existing `configureBibStrategy` tests both set `isPopoverVisible = false`, which is precisely the guard on the `lockScroll` call — so **no test reached that line at all**. Downstream, `auro-dialog`'s only scroll assertion used a `modal` dialog (still `"fullscreen"`, still locking, still green) and `auro-drawer` had no non-modal case.

Ten tests added in a new `describe("AuroFloatingUI scroll lock ownership (AB#1647843)")` suite:

1. `locks page scroll for a dismissible dialog above the breakpoint` — the AB#1625424 regression, asserting strategy `"dialog"` and all three overflow/position properties
2. `locks page scroll for a dismissible drawer above the breakpoint` — the AB#1625435 regression
3. `locks page scroll for a blocking dialog` — `modal` path unregressed
4. `locks page scroll below the fullscreen breakpoint` — mobile path unregressed
5. `leaves the page scrollable for a nested overlay` — `"cover"` must not lock
6. `leaves the page scrollable for a floating dropdown` — `"floating"` must not lock; guards the other consumers
7. `stays locked across repositions without re-saving the page styles` — simulates `autoUpdate` re-entry, and asserts `_savedScrollStyles` identity so a repeat lock cannot clobber the consumer's real page styles
8. `releases the lock when the bib is hidden` — `hideBib()` path
9. `releases the lock when the floater is torn down while open` — the `disconnect()` fix
10. `releases the lock even when the bib has already been detached` — the relaxed guard

Four more were added after code review surfaced fixes 4–6:

11. `releases the lock when an open overlay widens out of fullscreen` — the `else`-branch defect; locks below the breakpoint, then re-runs the strategy above it
12. `keeps the lock when configure() rewires the trigger while open` — the reconfigure defect
13. `still releases the lock on a real teardown` — the companion, pinning the `teardown: true` default
14. `mirrors aria-modal onto the inner dialog for the overlay strategies` — pins the one user-visible side effect, set on lock and removed on unlock

In `auro-dialog`, `keeps an open dialog intact when it is moved in the DOM (AB#1625424)` covers the reparent case.

The library suite is hermetic by construction: it snapshots and clears the six inline scroll properties in `beforeEach` and restores them in `afterEach`. This mattered immediately — the first run failed four tests with `expected 'fixed' to equal ''` because a pre-existing test (`lockScroll saves scroll position when locking`) locked and never unlocked, leaving `position: fixed` on the shared browser page for every test after it. That test now unlocks before finishing.

The same flaw was then found in the consumer suites, where it was better hidden. Their `snapshotPageScrollStyles()` helper saved and *restored* the page styles, so a leak from an earlier test was faithfully put back rather than cleared — and since most tests there never assert lock state, nothing failed. The dialog suite leaks from its very first test (`auro-dialog is accessible` opens a dialog and never closes it). Adding assertions made the leak visible as four unrelated-looking failures in the mobile pass. Both consumer helpers now snapshot *and clear*, matching the library suite.

**Revert-proofing.** Every fix was verified by reverting it in isolation:

| Reverted | Result |
|---|---|
| `lockScroll(value === "fullscreen")` restored | 6 of the new tests fail |
| `disconnect()` unlock removed | exactly 1 fails |
| `else`-branch unlock removed | `releases the lock when an open overlay widens out of fullscreen` fails |
| `configure()`'s `{ teardown: false }` removed | `keeps the lock when configure() rewires the trigger while open` fails |
| `auro-dialog` deferred teardown reverted | the reparent test fails in both viewports |

Full suites green with all in place: 123 Vitest + 156 browser tests in `auro-library`, 94 in `auro-dialog`, 116 in `auro-drawer`.

Two candidate fixes for the reconfigure defect were rejected because the suite caught them: guarding the unlock on `!isPopoverVisible` and on `!isConnected` both fail `releases the lock when the floater is torn down while open` — they reintroduce the very defect fix 2 addresses, since both conditions still hold during a genuine teardown.

### Section 5 — Risk Assessment

| Risk | Mitigation |
|---|---|
| Locking overlays that should not lock | Only `"fullscreen"` and `"dialog"` are affected; `"cover"` and `"floating"` take the other branch, asserted by two tests. `getPositioningStrategy`'s `default` case passes unknown behaviors through verbatim, so they never reach the overlay branch |
| Blast radius beyond the two reported components | `new AuroFloatingUI(this, <behavior>)` occurs in only `auro-dialog` and `auro-drawer`; every other consumer constructs with no behavior and resolves to `"floating"`/`"fullscreen"` |
| Repeated `autoUpdate` ticks re-locking and clobbering the consumer's saved page styles | `lockScroll` is guarded by `_scrollLocked`; asserted via `_savedScrollStyles` identity across three consecutive reconfigurations |
| Consumers with their own inline `body` styles losing them | Pre-existing values are captured in `_savedScrollStyles` and restored, not wiped; asserted with a pre-set `body { overflow: scroll }` |
| Scroll position jumping on close | `window.scrollTo(0, _savedScrollY)` on unlock, covered by the existing restore test |
| `aria-modal` now applied to non-modal overlays | Reviewed and accepted — both consumers already trap focus in non-modal presentations; documentation corrected in AB#1625424 |
| Lock stranded when a component unmounts while open | `disconnect()` now unlocks, and the unlock path no longer requires a live bib |
| Teardown unlock firing on a rewire instead of a real teardown | `disconnect({ teardown })` makes intent explicit; the default preserves every external caller, and both directions are asserted |
| `auro-dialog` teardown now deferred a microtask | Only reached on disconnect; a host that removes and re-inserts across separate tasks is still treated as a real unmount, which is the correct reading of that sequence. Two tests that called `disconnectedCallback()` directly were rewritten to remove the element for real |
| **Known, not fixed:** concurrent overlays corrupting each other's saved page styles | `_scrollLocked` and `_savedScrollStyles` are per-instance while `document.body` is global, so a second locker snapshots the already-locked page. Closing out of LIFO order leaves the page frozen with no owner. Latent before this change; this change widens exposure by making desktop non-modal overlays lock. Needs a single module-level owner (refcount or owner stack) — tracked separately, and no test yet instantiates two `AuroFloatingUI` instances |

### Key Lessons

1. **A gate that re-runs is not a one-time decision.** `configureBibStrategy()` is invoked by `autoUpdate` on every resize and scroll tick, which turned a wrong condition into an active, repeated *un*-locking. That is also why neither consuming component could patch around it locally. Before centralizing a behavior, check how often the deciding code path executes.

2. **Do not gate one concern on another concern's enum.** Scroll ownership was inferred from the positioning strategy because the two happened to coincide for the cases that existed at the time. When the strategy set grew a non-fullscreen overlay, the inference silently broke. `"fullscreen"` and `"dialog"` were already treated identically by every other line in the same branch — that inconsistency was the tell.

3. **Centralizing a behavior must move its tests too.** Both components deleted working scroll-lock code in favor of the library (`aeb1992`, `be314cb`) and deleted their coverage with it, while the library gained none. The behavior then had no owner asserting it in any repo. A shared-code migration is not complete until the guarantee is asserted where the code now lives, and re-asserted where it is consumed.

4. **Coverage that only exercises the working configuration is worse than none** — it produces a green suite that reads as proof. Both components had scroll-lock tests; both used the `modal` presentation, the only one that still worked. When adding a regression test, confirm it fails with the fix reverted.

5. **A shared resource needs one owner, not a rule applied at each call site.** Every defect here is the same shape: the page scroll lock is global, but the decision to take or release it was spread across `configureBibStrategy()`, `hideBib()`, `disconnect()`, and `configure()`, each deciding locally. Fixing one exposed the next — the lock branch and the unlock branch disagreed, then teardown and rewiring disagreed, and the per-instance snapshot still disagrees with itself when two overlays are open. When a fix keeps uncovering siblings, the bug is usually the ownership model rather than any one branch.

6. **One method serving two intents will eventually serve the wrong one.** `disconnect()` meant both "tear this down" and "rewire this," which was harmless until it acquired a side effect that only one of them wanted. The reachable-but-wrong caller existed for as long as the method did; the new side effect is what made it matter.

7. **A test-hygiene helper can hide the mess it was written to prevent.** The consumer suites' snapshot/restore helper preserved leaked page state by design, so a test that leaked was invisible to every test after it. It only surfaced once assertions were added that cared. Restoring prior state is right for values a test itself set; for global state a *previous* test may have corrupted, clearing is what makes a suite hermetic.

5. **Browser-environment tests share mutable global state.** A test that locks page scroll and never unlocks leaves `body { position: fixed }` on the page for every subsequent test in the run. Suites that mutate `document.documentElement` or `document.body` need to snapshot and restore, or they make later failures look like product bugs.
