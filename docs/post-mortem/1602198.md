# AB#1602198

## Executive Summary

Pop-up style elements in the Auro design system — dropdowns, comboboxes, selects, and menus — were silently broken whenever a page was served over a plain, non-secure web address (for example, loading the demo on a phone by typing the host computer's network IP instead of connecting via localhost). The elements would appear on screen but refuse to open or respond to any interaction.

This change fixes the failure by replacing a browser feature that only works on secure connections with one that works everywhere, while leaving the behavior on secure connections entirely unchanged. [AB#1602198](https://itsals.visualstudio.com/E_Retain_Content/_workitems/edit/1602198)

## The Problem

Modern browsers restrict certain APIs to "secure contexts" — pages loaded over HTTPS or from localhost. One of those restricted APIs, `crypto.randomUUID()`, was being used to assign internal identifiers to pop-up elements during initialization. When the page was served over a plain HTTP address (such as a LAN IP used for mobile device testing), calling that API threw an error that immediately aborted the initialization sequence. Every pop-up element on the page was left in a broken, non-interactive state as a result.

This was a hard failure rather than a graceful one: a single missing browser capability took down every floating element on the page. It also blocked the team from testing the design system on real mobile devices, which requires serving the demo over the local network.

## Root Cause

In `scripts/runtime/floatingUI.mjs`, `AuroFloatingUI.regenerateBibId()` called `window.crypto.randomUUID()` unconditionally to generate a unique element ID when none was already set. `crypto.randomUUID()` is specified to throw a `TypeError` in insecure contexts — and does so in all major browsers — so any page loaded over plain HTTP from a non-localhost origin hit this error every time a floating element was initialized.

## The Fix

Three changes were made:

1. A new shared helper, `generateUUID()`, was added at `scripts/runtime/generateUUID/generateUUID.mjs` (re-exported via `scripts/runtime/generateUUID/index.mjs`). It tries three approaches in order:
   - **Secure context:** calls `crypto.randomUUID()` natively (unchanged behavior for HTTPS/localhost).
   - **Insecure context with `getRandomValues`:** constructs a valid RFC 4122 v4-format UUID by drawing 16 random bytes from `crypto.getRandomValues()`, then setting the required version and variant bits.
   - **Last resort (no crypto API at all):** builds a v4-format UUID by shifting through the bits of `new Date().getTime()`.

   In all three cases, if the resulting UUID begins with a digit, the first character is replaced with `'a'` so the ID is valid in CSS selectors without escaping.

2. `regenerateBibId()` in `scripts/runtime/floatingUI.mjs` was updated to call `generateUUID()` instead of `window.crypto.randomUUID()` directly.

3. A JSDoc block was added to `generateUUID()` documenting the three-tier design rationale and linking to the W3C spec for the secure-context restriction.

## Why This Works

`crypto.getRandomValues()` is available in all browsers regardless of secure-context status — it is not restricted the way `randomUUID()` is. The v4 UUID constructed from it is cryptographically random in all the ways that matter for element IDs (uniqueness, no guessable sequence). The fix never assigns to or patches `window.crypto`, so it cannot interfere with any consumer's use of the Crypto API. Secure contexts continue to use native `randomUUID()` through the first branch of the helper, so there is no regression on HTTPS or localhost.

The leading-letter guarantee matters because CSS selectors using IDs require the ID to start with a letter — a leading digit such as `3f2a…` would require escaping (`#\33 f2a…`) in any CSS or `querySelector` call. Replacing a leading digit with `'a'` preserves the full length and format of the ID while making it unambiguously safe as a CSS selector target.

## Outcome

Auro floating elements — dropdowns, comboboxes, selects, and menus — now initialize and respond to interaction when the page is served over a plain HTTP address. There is no visible change for users on secure pages. Mobile device testing over the LAN is unblocked.

**Resolved**
- **`generateUUID()` helper added** — `scripts/runtime/generateUUID/generateUUID.mjs` implements all three tiers (native randomUUID → getRandomValues → Date.getTime()), guarantees a letter-initial ID for CSS selector safety, and is re-exported via `index.mjs`.
- **`regenerateBibId()` uses the helper** — `scripts/runtime/floatingUI.mjs` now imports and calls `generateUUID()` instead of `window.crypto.randomUUID()`, so floating elements initialize in insecure contexts.

## Learnings

- `crypto.randomUUID()` is a secure-context-only API and must never be called unconditionally in library code that may run on non-localhost HTTP. Always guard UUID generation behind an insecure-context fallback.
- `crypto.getRandomValues()` is the correct insecure-context fallback — it is available everywhere and produces cryptographically random bytes suitable for element IDs.
- A single unguarded API call in an initialization path can silently break every component that depends on it. Hard failures in element initialization should be narrowed to the smallest possible scope.
- Element IDs generated for use in CSS selectors must start with a letter. A UUID whose first nibble is a digit (`0`–`9`) is valid as an HTML attribute value but requires escaping in CSS — always guarantee a letter-initial ID at the point of generation rather than at each call site.
- The fix spans two repos (auro-library and auro-formkit). Shipping the library change first is safe because each repo's call sites are independent, but the formkit follow-on should be tracked to avoid a lingering inconsistency.
- Vitest is the right tool for testing pure utility functions like `generateUUID()`: no DOM required, easy to stub `crypto` properties with `vi.spyOn(..., 'get')`.
- `Math.*` broadly may be prohibited by company security policy, not just `Math.random()`. When using `new Date().getTime()` as a fallback entropy source, shift through its bits using arithmetic integer division (`(d - r) / 16` where `r = d % 16`) rather than `Math.floor(d / 16)` — this avoids all `Math.*` usage while remaining correct for 44-bit timestamp values that would overflow 32-bit bitwise operators.

## Iterations That Didn't Work

**Tier 3: multiple iterations toward a `Math.*`-free implementation.**
1. **`((Date.now() * Math.random() * 16) % 16) | 0`** — original approach. Dropped after a code review proved `Date.now()` was mathematically canceled by `% 16`, making it equivalent to `Math.random()` alone.
2. **`(Math.random() * 16) | 0`** — simplified form. Dropped when `Math.random()` was flagged as prohibited by company security policy.
3. **`Math.floor(d / 16)`** — used in the first Date-based implementation to shift bits. Dropped when it was clarified that the policy covers `Math.*` broadly, not just `Math.random()`. Replaced with arithmetic integer division `(d - r) / 16` (where `r = d % 16`), which is exact for all positive integers and avoids all `Math.*` usage.
